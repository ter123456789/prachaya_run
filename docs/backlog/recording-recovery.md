# กู้กิจกรรมที่ค้าง เมื่อแอปถูกปิดหรือเครื่องดับระหว่างบันทึก (Recording Journal)

สถานะ: **แนวคิด ยังไม่ได้ลงมือ** — คุยไว้ 2026-10-13

## ปัญหา

| สถานการณ์ | ตอนนี้ | ทำอะไรได้ |
|---|---|---|
| ปิดหน้าจอ / ล็อกเครื่อง | ✅ บันทึกต่อได้ (Android foreground service + wake lock, iOS `allowBackgroundLocationUpdates` + `UIBackgroundModes: location`; เวลาคิดจาก `clock()` ไม่ใช่ tick) | — |
| แอปถูกปิดกลางทาง (OS ฆ่าเพื่อคืนแรม, ผู้ใช้ปัดทิ้ง, แครช) | ❌ ข้อมูลทั้งรอบหาย (`RecordingSession` อยู่ในหน่วยความจำอย่างเดียว) | กู้คืน |
| เครื่องดับจริง (แบตหมด) | ❌ ข้อมูลทั้งรอบหาย | กู้ได้ถึงจุดก่อนเครื่องดับ |

แก้ด้วยการ **"ทำให้ข้อมูลไม่หาย"** ไม่ใช่ "ทำให้แอปไม่ตาย" (แนวเดียวกับ Strava / Garmin / NRC)

### ทำไมไม่ทำให้แอปรันต่อหลังถูกฆ่า
- iOS: ผู้ใช้ปัดแอปทิ้ง ระบบหยุด GPS ทันที ปลุกกลับได้แค่ significant location change ซึ่งแม่นระดับหลายร้อยเมตร ใช้วาดเส้นทางไม่ได้
- Android: ต้องย้ายการบันทึกทั้งหมดไป service แยก isolate และรื้อ `RecordBloc` ใหม่ แต่ Xiaomi/Oppo ก็ยังฆ่าได้อยู่ดี ไม่คุ้ม

## แนวคิด

### 1. จดลงดิสก์ระหว่างบันทึก
- ตอนกดเริ่ม: จด activity id (สร้างตอนนี้เลย), ประเภท, เวลาเริ่ม
- ระหว่างวิ่ง: จดจุด GPS เป็นระยะ (เช่น ทุก 10 วินาที หรือทุก 20 จุด)
- จดทันทีเมื่อ: หยุดชั่วคราว, ทำต่อ, แอปเข้า background (`AppLifecycleState.paused` — จังหวะก่อนถูกฆ่าบ่อยที่สุด)
- จดเป็น **เหตุการณ์** (จุด / หยุด / ทำต่อ) แล้วตอนกู้ให้เล่นซ้ำผ่าน `RecordingSession` ตัวเดิม ตัวกรองจุด GPS และการคำนวณระยะทางจึงอยู่ที่เดียว
- เครื่องดับ = เสียข้อมูลไม่เกินช่วงจดล่าสุด

### 2. เปิดแอปครั้งถัดไปแล้วเจอสมุดค้าง
แสดงหน้าต่างถาม "พบกิจกรรมที่ยังไม่จบ วิ่ง 5.2 กม. เมื่อ 07:12":
- **บันทึกเลย** — ตัดจบที่จุด GPS สุดท้าย (ไม่ใช่เวลาที่เปิดแอปใหม่)
- **ทำต่อ** — กลับหน้าบันทึกในสถานะหยุดชั่วคราว ช่วงที่แอปตายนับเป็นช่วงหยุด ไม่ใช่เวลาเคลื่อนที่
- **ทิ้ง**
- สั้นเกินเกณฑ์ของ `SaveActivity` (`ActivityTooShortException`) → ทิ้งเงียบ ๆ ไม่ต้องถาม

### 3. กันบันทึกซ้ำ
- activity id สร้างตั้งแต่ตอนเริ่มและอยู่ในสมุด ถ้าแอปตายหลังบันทึกเสร็จแต่ก่อนลบสมุด การกู้ครั้งถัดไปจะเขียนทับ id เดิม (upsert) ไม่เกิดกิจกรรมซ้ำ
  - ต้องให้ `SaveActivity` รับ id จากภายนอกได้ (ตอนนี้สร้าง id เอง)
- ลบสมุดก็ต่อเมื่อบันทึกเสร็จจริงเท่านั้น

### 4. วางตามสถาปัตยกรรมเดิม
- domain: port `RecordingJournal` — `append` / `loadPending` / `clear`
- data: ตาราง SQLite ใหม่ → **DB v5** (+ migration test บน `sqflite_common_ffi`)
- presentation: `RecordBloc` เรียก journal; หน้าต่างกู้คืนบน dashboard
- สมุดเป็นของเครื่อง ไม่ผูกบัญชี ตอนบันทึกใช้บัญชีที่ล็อกอินอยู่ตามปกติ (`owner_id` ตามกติกาเดิม)

## งานประกอบ (ทำแยกได้)
- หน้าแนะนำปิด battery optimization บน Android (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` หรือคู่มือตามยี่ห้อ) — ลดโอกาสถูกฆ่าตั้งแต่แรก
- ขอสิทธิ์ `POST_NOTIFICATIONS` ตอนรันไทม์บน Android 13 ขึ้นไป (ประกาศใน Manifest แล้ว แต่ยังไม่ได้ขอ)
- ปุ่ม "จำลองแอปถูกฆ่า" ใน Debug Panel (`features/debug`) — ทดสอบการกู้คืนโดยไม่ต้องไปวิ่งจริง

## คำถามที่ยังต้องตัดสินใจ
1. มีตัวเลือก "ทำต่อ" ไหม หรือแค่ "บันทึก / ทิ้ง" (แบบหลังง่ายกว่ามาก)
2. ถ้ามี "ทำต่อ" ควรหมดอายุไหม (เช่น เกิน 1 ชั่วโมง → เหลือแค่บันทึก/ทิ้ง)
3. ช่วงจดลงดิสก์ 10 วินาทีพอไหม (ถี่กว่า = เสียข้อมูลน้อยลง; ผลต่อแบตน้อยมากอยู่แล้ว)
4. ทำหน้า battery optimization ไปพร้อมกันไหม
